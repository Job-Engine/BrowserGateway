Domain model

Three dimensions. A platform is a site the gateway can drive. An action is defined once per platform and owns the contract. A client is a whitelabel login, optionally with navigation-only overrides. The output shape never bends to a client.

Platform
lightreach

A website the gateway can operate. Owns a vault and a client roster.

Action
milestoneStatus

One task. Owns inputSchema, buildGoal, and a locked extractSchema. Variants are input enums.

Client
lgcyco, brandx, ...

A whitelabel login identity. May override navigation only, never the answer shape.

Worked example: lightreach.milestoneStatus

The base action

"lightreach.milestoneStatus": {
  startUrl: "https://palmetto.finance/accounts",
  requiresLogin: true,
  timeout: 60000,
  inputSchema: z.object({
    name: z.string(),
    address: z.string(),
    milestone: z.enum(
      ["NTP","PTO","Install","Permit"]),
  }),
  buildGoal: (i) =>
    `Look up ${i.name} at ${i.address}.
     Verify name AND address.
     Read the ${i.milestone} status
     field exactly. Read-only.`,
}

One action covers every milestone. A new milestone is one enum value, not a new entry.

Clients never change the answer shape. Callers get one shape per action, always.

{
  milestone:      string,
  value:          string | null,
  matchVerified:  boolean,
  matchedName:    string,
  matchedAddress: string
}
The escape hatch. Overrides adjust navigation only: label maps, start URL, goal hints, timeout. If a client's layout diverges so far that even the data shape changes, that is a new action with the client pinned to it, never an override.

Credentials

The container holds only vault-scoped service account tokens. Every login is fetched per run and thrown away. Whitelabel means one login item per platform.client pair.

The three rules of one

One vault per domain

Finance portals in Portals, gov and utility sites in GovSites. A leaked token exposes one domain, not everything.

One item per platform.client

Named platform.client (lightreach.lgcyco, lightreach.brandx). Fields: username, password, one-time password. 5 to 7 clients per platform is the expected shape.

One service account per vault

The service account token is the only long-lived secret in the container. Rotation happens in 1Password with no code change.

Values are injected as variables the model references by name. They are never part of an LLM prompt, never written to disk, redacted in logs, and dropped from memory after the run.

The OTP rule

Time-based codes rotate every 30 seconds, so a cached code is a broken code. TOTP is never cached. Each run reads a fresh code at login time.

Rotation story

A password changes upstream, you fix the item in 1Password, and the next run picks it up. No redeploy, no env edit, and the audit trail comes for free.

Two non-negotiables. Never the 1Password browser extension inside a Browserbase session: it needs a persistent desktop app and cannot run in an ephemeral cloud browser. And Contexts (one per platform.client) are a fast path that skips login, but sites force logouts, so JIT credentials stay the reliable fallback.

API

Async plus poll. Callers send business data and a client, get a jobId, and poll until done. Bearer auth with per-caller tokens; scopes are useCase by client.

Status semantics

success

Goal met, record match verified, data extracted. A legitimately blank field still counts as success.

failure

Ran cleanly with a negative business outcome (no match, missing record). Callers may automate on this.

error

System, auth, or navigation problem. Callers alert on this. Failure and error are never conflated.

Onboarding

Three sizes of change. None of them touch server, secrets, or the runner. The core stays generic; portal knowledge lives in the catalogue and 1Password.

1Minutes

Add a client to an existing platform

The common case: another whitelabel brand on a platform you already automate.

Cost: one catalogue entry plus one 1Password item (username, password, OTP). No new code. Callers pass client: "newbrand".

2Hours

Add a client that needs overrides

Same brand-on-a-platform case, but the layout differs enough to need navigation help.

Cost: the catalogue entry and 1Password item, plus a navigation override (label map, start URL, goal hints, timeout). The extract schema stays locked.

3Days

Add a new platform

A site the gateway has never driven.

Cost: a domain vault and service account, one login item per client, a new action recipe (schemas, goal, risk, limits), and a first-live-run test against a known record.

The first-live-run rule. No action goes live until it has run against a known record and the labels are confirmed. Field labels and login flows are assumptions until a session replay proves them.

For AI agents

This system is designed to be agent-legible. The canonical context is small, versioned, and machine-readable, so an agent can orient itself without guessing.

AGENTS.md

At the repo root. The source of truth for what the system is, what it must become, and the rules that are not yours to change.

GET /catalogue

The live registry: platforms, actions, variants, and clients. What the running gateway can actually do right now.

GET /openapi.json

The machine-readable API description (planned). Endpoint shapes, request bodies, and the envelope contract.

How an agent should orient
  1. Read AGENTS.md at the repo root, including the manifest below and the locked decisions.
  2. Read the architecture review (BrowserGateway/architecture-review-2.0.docx) for findings, target modules, and build order.
  3. Hit GET /catalogue to see what the running gateway can do today.
  4. Run the tests (npm run typecheck, npm test) before changing anything.
