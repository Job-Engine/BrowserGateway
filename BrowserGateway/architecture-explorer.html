Browser Automation Gateway

A general internal service: apps send {useCase, client, input}, the gateway resolves the action from the catalogue, the login from 1Password (one item per platform + client, whitelabel-aware), runs the browser on Browserbase, and returns one normalized envelope. LightReach is the first platform, not the boundary.

The catalogue: platforms, actions, clients

Three dimensions. A platform is a site the gateway can drive. An action is defined once per platform and owns the contract. A client is a whitelabel login on that platform, optionally with navigation overrides. The core (server, secrets, runner) stays generic.

What one action contains

FieldDrives
keyNamespaced id, e.g. lightreach.milestoneStatus
inputSchemaZod validation, including variant enums like milestone: enum(NTP, PTO, Install, Permit)
buildGoal(input)Natural language goal with business data and variant merged in
extractSchemaShape of data in the envelope. Locked: clients can never override it
url, requiresLoginBase start page and credential behavior
risk, timeout, attemptsPer-action tightening of runner policy

Example: lightreach.milestoneStatus

"lightreach.milestoneStatus": {
  url: "https://palmetto.finance/accounts",
  requiresLogin: true,
  inputSchema: z.object({
    name: z.string(),
    address: z.string(),
    projectId: z.string().optional(),
    milestone: z.enum(
      ["NTP","PTO","Install","Permit"]),
  }),
  extractSchema: { milestone, value,
    matchVerified, matchedName, ... },
  buildGoal: (i) =>
    `Look up ${i.name} at ${i.address}.
     Verify name AND address.
     Read the ${i.milestone} status
     field exactly. Read-only.`,
}

One action covers every milestone. A new milestone is one enum value, not a new entry.

Client overrides (whitelabel)

Each platform carries a client roster. A client may override navigation only:

clients: {
  lgcyco:  {},                // base
  brandx:  { overrides: {
    milestoneStatus: {
      labels: { "NTP Date":
        "Notice to Proceed Date" },
      hints: "Status fields live in
        the right-hand rail.",
    }}},
  voltic:  { overrides: {
    milestoneStatus: { url:
      "https://voltic.palmetto..." }}},
}

Merged at job time: base action + client override = effective run config. extractSchema never merges; callers get one shape per action, always.

How resolution works

1. Caller posts {useCase, client, input}.

2. getEntry(useCase) finds the action; unknown key fails fast.

3. inputSchema validates input including the variant enum.

4. Credentials resolve from op://<vault>/<platform>.<client>.

5. buildGoal(input) plus override labels/hints become the agent instruction.

The escape hatch: if a client's layout diverges so far that even the data shape changes, that is a new action, not an override, with the client pinned to it.

Adding a platform, action, or client

Three onboarding sizes. None of them touch server.ts, secrets.ts, or runner.ts.

1

New client on an existing platform

The most common case: another whitelabel brand on a platform you already automate.

Vault:  Portals
Item:   lightreach.newbrand
Fields: username, password,
        one-time password (2FA)

Add the client to the platform's roster (with overrides only if its layout differs). No new action code. Callers pass client: "newbrand".

2

New action on an existing platform

One block in catalogue.ts: schemas, goal builder, risk and limits.

"lightreach.docsList": {
  inputSchema: z.object({
    name: z.string(),
    address: z.string() }),
  extractSchema: { documents: [...] },
  buildGoal: (i) => `Open the verified
    record's documents tab and list
    every document. Read-only.`,
}

Every existing client can run it immediately; add overrides only where a brand's layout differs.

3

New platform

Pick or create the domain vault, add one login item per client, then write the first action.

1. Vault (per domain):  GovSites
2. Items: govnet.default, ...
3. Service account scoped
   to that vault only
4. First action in catalogue.ts
5. Deploy, live test vs a
   known record
4

Callers use it immediately

curl -X POST $GW/jobs \
 -H 'content-type: application/json' \
 -d '{"useCase":
        "lightreach.milestoneStatus",
      "client": "newbrand",
      "input": {
        "name": "Jane Homeowner",
        "address": "123 Solar Way...",
        "milestone": "NTP" }}'

Same envelope, same polling, same error codes. Caller scopes are granted per useCase x client.

First live run rule: every new platform, action, or divergent-layout client gets tested against a known record before callers rely on it. Field labels and login flows are assumptions until a session replay proves them.

Credentials: just-in-time from 1Password

The container holds only service account tokens, one per vault. Everything else is fetched per run and thrown away. Whitelabel means one login item per platform + client pair.

The flow, per job

1. Runner asks resolvePortalCredentials(platform, client).

2. secrets.ts checks its 60 second cache, keyed by platform + client.

3. On a miss: op read op://<vault>/<platform>.<client>/username, /password, and /one-time password?attribute=otp if present.

4. Values are injected as Stagehand variables: typed into the login form, never included in any LLM prompt, redacted in logs.

5. After the run they fall out of memory. Runs sharing a login are serialized so sessions never log each other out.

Vault strategy

One vault per domain: finance portals in Portals, gov and utility sites in GovSites, and so on. Portals was first; it is not special.

One item per login: named platform.client (lightreach.lgcyco, lightreach.brandx, ...). 5 to 7 clients per platform is the expected shape.

One service account per vault: a leaked token exposes one domain, not every credential the company has.

Never: the 1Password browser extension inside Browserbase sessions. It needs a persistent desktop app and cannot work in an ephemeral cloud browser.

Why this beats the alternatives

vs env vars per login: 7 clients x 10 platforms = 70+ credential pairs. Env vars cannot manage that; the vault can. Rotation without redeploys, audit trail included.

vs storing creds in a hosted agent: hosted Browserbase agents cannot cleanly do op CLI injection, which is exactly why the runner is self-hosted Stagehand.

vs pre-warmed Contexts only: Contexts (one per platform + client) skip login but sites force logouts; JIT creds stay the reliable fallback.

Local dev and next steps

No token set? secrets.ts falls back to PORTAL_<KEY>_USERNAME / _PASSWORD / _OTP env vars so the full path is testable before 1Password is wired.

Planned hardening: swap the op CLI for the 1Password SDK in the long-running service, sanitize subprocess errors so tokens never reach logs, and pass item IDs instead of names in hot paths to stay under service account rate limits.

The API callers see

Async plus poll. Callers send business data plus a client, get a jobId, poll until done. Bearer auth via GATEWAY_TOKEN; scopes are useCase x client.

Status semantics

StatusMeaning
successGoal met, data extracted and verified
failureRan cleanly, negative outcome (no match, blank field)
errorSystem, auth, or navigation problem

The envelope (stable across all use cases)

{
  "jobId": "...",
  "useCase": "lightreach.milestoneStatus",
  "client": "lgcyco",
  "status": "success | failure | error",
  "data": {
    "milestone": "NTP",
    "value": "2026-06-30",
    "matchVerified": true
  },
  "error": {
    "code": "MATCH_FAILED",
    "message": "...",
    "fields": ["address"]
  },
  "meta": {
    "sessionId": "...",
    "sessionReplayUrl": "...",
    "credentialItem":
      "op://Portals/lightreach.lgcyco",
    "ranAt": "...",
    "durationMs": 0,
    "attempts": 1
  }
}

Every response carries the Browserbase session id, replay URL, and which credential item ran, so any failure can be traced to a brand and watched back.

Known gaps (by design, for now): the job store is in-memory (swap for Redis/Postgres before multiple replicas), there is no queue in front of Browserbase concurrency caps, and callers poll because webhooks do not exist yet.
